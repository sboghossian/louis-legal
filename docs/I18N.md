# Louis — Internationalization (i18n)

Louis ships its UI chrome in 11 languages. The system is intentionally
tiny: one TypeScript dictionary, one React context, one boot script. No
ICU, no MessageFormat, no async loaders. Adding a string takes one
commit; adding a language takes about an hour.

## The translator pattern

All UI strings live in `frontend/src/i18n/dictionaries.ts`. Every string
is keyed by a stable English-language slug (`nav.home`,
`vault.setup.title`) and translated into 10 other locales in the same
file.

At runtime, components call the `t()` function from `useLocale()`:

```tsx
import { useLocale } from "@/contexts/LocaleContext";

export function SignInButton() {
    const { t } = useLocale();
    return <button>{t("action.sign_in")}</button>;
}
```

### Interpolation

`t()` accepts a second argument that injects values into `{name}` slots:

```tsx
t("home.welcome.named", { name: "Stéphane" });
// → "Bon retour, Stéphane. Sur quoi travaillons-nous aujourd’hui ?"

t("prompts.showing", { count: 12, total: 240 });
// → "Showing 12 of 240 prompts"
```

Slot names are mechanical — they're substituted as `String(value)` with
no escaping. If you need a colored variable, split the string into
chunks or render as JSX rather than putting markup inside the
dictionary.

### Fallback semantics

If a key is missing in the active locale, `lookup()` falls back to
English. If it's missing in English too, the key itself is returned.
That means **adding a new English string never crashes the app for a
non-English user** — they just see the English copy until the
translation lands. Adding new locales is similarly safe: an empty
French dictionary would render as fully English.

### Locale switching

The locale is determined in this order:

1. Server profile `appearance.language` (if signed in).
2. `localStorage.louis.locale` (signed-out users).
3. The first two letters of `navigator.language`, if supported.
4. `"en"`.

`<LocaleProvider>` wraps the whole app in
`frontend/src/components/providers.tsx`. The first paint is already
correct because `LOCALE_BOOT_SCRIPT` (inlined in
`frontend/src/app/layout.tsx`) sets `<html lang>` and `<html dir>`
synchronously before React hydrates. That avoids the FOUC where an
Arabic user briefly sees an LTR layout.

The picker that users see is in **Settings → Appearance → Language**
(`appearance.language`), and `setLocale()` persists both to the server
profile (when signed in) and to localStorage.

forms preferred where Iberian Spanish would feel formal).

### RTL

`RTL_LOCALES = ["ar"]`. When the active locale is in that list the
boot script writes `<html dir="rtl">`, which flips Tailwind's
`rtl:`-prefixed utilities and the browser's default text direction.
The Arabic strings themselves contain no manual bidi marks — the
browser does the right thing once `dir="rtl"` is in place.

A separate RTL DOM polish pass (mirroring icons, swapping `pl-*` for
`pe-*` in components that haven't been migrated to logical properties,
adjusting hard-coded `text-left`) is tracked outside this task.

## Pluralization

We deliberately do **not** ship a full ICU MessageFormat runtime — it
would more than triple the bundle size of `dictionaries.ts` and the
chrome doesn't need it.

For the handful of strings that have a number-and-noun ("showing X of
Y prompts"), each locale uses its own naturally-correct phrasing,
trading precision for size. Languages with rich plural rules (Russian
with three forms, Arabic with six, Polish with three) use the safest
"X из Y" / "{count} من {total}" form that reads correctly for any
count.

If you ever need true plural branching (e.g. "1 matter" vs "5 matters"
vs Russian's "2/3/4 дела" vs "5–20 дел"), branch at the call site
rather than expanding the dictionary:

```tsx
const label =
    count === 1
        ? t("matters.count_one", { count })
        : t("matters.count_other", { count });
```

## How to add a new locale

1. Add the two-letter code to the `Locale` union in
   `frontend/src/i18n/dictionaries.ts`.
2. Add an entry to `LOCALES` (`code`, English `label`, `native` name).
3. If the language is right-to-left, add the code to `RTL_LOCALES`.
4. Copy `en` to a new `const xx: Dict = { ... }` block and translate
   every value.
5. Add `xx` to the `DICTIONARIES` object at the bottom of the file.
6. No other code changes required. `LocaleContext`, the picker, and
   the boot script all read from `LOCALES` and `DICTIONARIES`
   automatically.

Smoke test by setting `localStorage.louis.locale = "xx"` in DevTools
and reloading — every page should render in your new locale, and
RTL layouts should flip if applicable.

## Adding a new string

1. Add the key + English value to the `en` dictionary.
2. Add the same key with a translated value to **all 10 other
   dictionaries**. The audit script at the end of this doc fails CI if
   you forget.
3. Replace the hardcoded string in the source component with
   `t("your.key")`.

Keep keys descriptive and namespaced (`vault.setup.too_short`, not
`error1`). Keep them short — they're written more than read.

### Translation philosophy

- Translate UI chrome: nav, buttons, settings labels, error toasts.
- Do **not** translate proprietary nouns: "Louis", "Drafting Board",
  "Tabular Review", "Newsfeed".
- Do **not** translate technical terms used as-is in industry:
  `MCP`, `API key`, `AES-256`, `AGPL`, `MIT licensed`, `BYO`,
  `OAuth`, `PBKDF2`, `SSE`. They stay in English in every locale.
- Legal domain terms get a native legal translation, not a literal
  one: "matter" → French `dossier` (not `matière`); "vault" →
  `coffre-fort` (not `voûte`); "redline" → `annotation` /
  `Anmerkung`.
- Don't put HTML or React in dictionary values. Split into adjacent
  keys and render them in JSX.

## Audit script

```bash
# from repo root
node -e '
import("./frontend/src/i18n/dictionaries.ts").then(m => {
    const en = Object.keys(m.DICTIONARIES.en);
    for (const [loc, d] of Object.entries(m.DICTIONARIES)) {
        const missing = en.filter(k => !(k in d));
        if (missing.length) console.log(loc, "missing", missing.length, missing);
    }
});'
```

The shorthand audit (no TypeScript loader) is plain `grep`:

```bash
grep -c '^    "' frontend/src/i18n/dictionaries.ts
# 11 × N keys should match N × 11
```

### What stays English (intentional, per dictionary philosophy)

- Long-form prose pages: `/transparency`, `/about`, `/docs`,
  `/help`. These read like legal copy + product manifestos and the
  current approach is to ship them in English until a content team
  takes a translation pass.
- Auth pages (`/login`, `/signup`, `/auth/*`) and the marketing
  landing (`/page.tsx`). Out of scope for this task.
- Catalog data inside `customize/page.tsx` (the 200+ source/tool
  labels + descriptions), `legal-flows/page.tsx` templates,
  `clauses/page.tsx` rows, `skills/page.tsx` IDs, `matters/page.tsx`
  table rows. Translating these would require translating product
  data, which is out of scope.
- Console logs, error stack traces, code identifiers (skill IDs,
  CM numbers, cron expressions).
